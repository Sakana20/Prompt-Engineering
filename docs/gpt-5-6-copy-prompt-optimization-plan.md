# GPT-5.6 文案 Prompt 减约束优化方案

## 结论

当前项目的问题不是缺少规则，而是同一生成请求同时叠加了基础模板、项目配置、Skill 规则、
学习块规则和确定性校验说明。大量内容重复描述“应该怎么写”和“不要怎么写”，使模型优先满足
局部句式要求，而不是理解商品、受众和传播目标，因此生成结果容易规整、僵硬、同质化。

建议把文案生成改成“少量硬边界 + 清晰创作目标 + 精简任务上下文 + 生成后确定性校验”：

- 项目配置只保存事实、活动口径、受众、传播目标和少量风格方向；
- 法律、事实、利益点原文、禁用活动口径和下游格式继续作为硬约束；
- 不再用配置文件规定固定叙事流程、固定开头、固定结尾和大量逐句写法；
- 正面告诉 GPT-5.6 什么结果算好，避免堆叠几十条反向禁令；
- 先生成自然候选，再由现有 CLI 做确定性校验；校验失败只反馈命中的具体问题，不把整套规则
  再次追加给模型；
- 每次只删除或调整一组约束，用同一组真实素材做对照评测，而不是一次性重写全部 Prompt。

这符合 OpenAI 对 GPT-5.6 的建议：使用更精简的 Prompt、每条指令只陈述一次、保留真正代表
产品要求或已证实能修复质量问题的示例，并让模型根据上下文推断实现细节。官方同时建议用
代表性任务比较修改前后的成功率、完整性、token、延迟和成本，而不是假设更多指令会带来更好
结果。

## 当前链路为什么比网页版 GPT 更僵硬

网页版 GPT 通常接收到的是用户目标、少量背景和一个直接请求，模型有空间理解“我要一条自然
口播”的真实意图。当前项目则在一次文案请求中合并了以下内容：

1. `configs/projects/*.json` 中很长的 `tone`、`point_of_view`、`sentence_style`、
   `emphasis`、`avoid_phrases` 和 `extra_rules`；
2. `copywriting_prompt.txt` 中重复的内容比例、口语要求、负面示例、学习块用法和校验说明；
3. `SKILL.md` 与 `copywriting-rules.md` 中另一份相近规则；
4. 本次筛选出的真人原文块；
5. 活动事实、利益点、当前季节、禁止表达和行动引导规则；
6. 80–100 字、三种 copy mode、50% 改写比例、来源字段等下游合同。

其中只有一部分必须在“创作时”出现。其余内容属于 CLI 操作说明、审计字段或生成后的校验逻辑，
不应全部进入给模型的创作 Prompt。

### 主要过度约束点

#### 1. 同一目标被重复陈述

“生活化”“商品是重点”“像朋友分享”“句子短”“不要详情页语气”等要求同时出现在默认
`LanguageStyle`、项目 JSON、基础模板和 Skill 中。重复并不会让风格更自然，反而提高这些词在
模型决策中的权重，促使模型机械套用一个安全、规整的中间答案。

#### 2. 项目配置把创作策略写成了执行脚本

例如固定要求：

```text
钩子/共鸣 → 生活矛盾 → 原本打算 → 平台和利益点 → 商品动作 → 情绪收尾
```

这不是活动事实，而是一种可选创意路径。把它设为所有文案的统一逻辑，会导致不同商品只是在
同一结构中换名词。

#### 3. 负面词和负面句式过多

当前配置列出大量 `avoid_phrases`，基础模板又重复部分内容。长负面列表会让 Prompt 的注意力
集中在“不要写什么”，却没有给模型足够自由去判断“这次最自然的说法是什么”。

应只保留两类负面项：

- 合规或业务上绝对不能出现的内容；
- 经过真实回归证明会高频复发的少量失败模式。

一般审美偏好不应成为硬词库。例如“不突兀”“看着清爽”可能在某一批中重复，但不代表它们在
所有商品、所有上下文中都错误。

#### 4. 生成规则和审计规则混在一起

`copy_mode`、`source_block_id`、`source_slot_values`、`rewrite_anchor_phrases` 是任务清单和
校验合同；模型需要知道本条采用哪种模式及其关键要求，但不需要在每次创作时阅读所有字段的
完整解释和失败处理流程。

#### 5. 软风格被当成硬验收

“前三秒必须怎样”“平台必须后置”“结尾必须落在某类生活状态”“必须出现行动引导”等要求，
只有在明确的投放策略或合规合同要求时才应为硬约束。否则它们应是创意偏好，让模型在适合时
采用，而不是每条逐项打卡。

#### 6. 字数目标可能放大模板腔

80–100 字如果是下游配音或投放的刚性合同，可以继续硬校验；如果只是经验范围，建议改成
目标区间与容忍区间：例如目标 80–100 字，70–110 字可进入人工复核。模型为了硬凑字数时，
最容易添加“很方便、很省心、日常很合适”一类无信息句。

## GPT-5.6 Prompt 设计原则

### 原则一：描述结果，不规定逐步写法

GPT-5.6 的意图理解更强，官方建议继续提供领域上下文、硬约束、成功标准和重要歧义的处理方式，
但通常不必规定每一步如何执行。

应写：

```text
成稿要像一个真实的人在分享这次为什么会买、拿到后怎么吃或怎么用；商品和利益点都要自然可听，
但不能像活动播报。每条选择一个最贴合商品的生活切口，自行组织顺序。
```

不应写：

```text
第一句必须钩子，第二句必须生活矛盾，第三句平台后置，最后一句必须情绪或习惯收尾。
```

### 原则二：一条规则只出现一次

同一条规则必须有唯一权威层：

| 内容 | 唯一权威位置 | 是否进入创作 Prompt |
| --- | --- | --- |
| 商品事实 | 项目配置/本次用户输入 | 是 |
| 活动事实与利益点 | 项目配置 | 是 |
| 合规禁用项 | ValidationConfig | 只给精简摘要，生成后硬校验 |
| 文案目标与成功标准 | 基础 Prompt 模板 | 是 |
| 项目风格差异 | 项目配置的精简 creative brief | 是 |
| 学习原文 | 正式学习库的本次筛选块 | 是，仅少量 |
| copy mode 字段合同 | Schema 与验证器 | 只给当前模式所需部分 |
| 发布、审核、CLI 操作 | Skill/runtime 文档 | 否 |

### 原则三：硬约束与创意偏好分开

建议在领域模型中明确两类内容，即使首版只在文档层设计：

#### 硬约束

- 不虚构商品、品牌、价格、销量、功效、配送和促销事实；
- 必填利益点必须出现；
- `exact_match` 和 `NO_SPLIT` 必须保持；
- 禁用活动口径不得出现；
- 不得出现未经确认的实时天气；
- 最终输出合同和付费边界；
- 真正由法务、平台或下游要求确定的长度和格式。

#### 创意偏好

- 生活化、口语化；
- 福利前置或后置；
- 更活泼或更克制；
- 可参考的人群、场景、节奏和切口；
- 希望减少但不是绝对禁止的套话。

创意偏好不应直接产生失败状态。它们更适合用于候选排序、人工评分或批次质量报告。

### 原则四：正面成功标准优先于长禁令

建议只保留 4–6 条可观察的成功标准：

1. 听起来像真人在说，不像商品说明或活动播报；
2. 有一个具体购买或使用动机，且与该商品匹配；
3. 商品事实清楚，但不连续罗列参数；
4. 利益点自然嵌入人物当下的决定；
5. 每句话提供新信息，没有为凑字数添加的空话；
6. 同批文案在人设、切口、节奏或情绪上有实际差异。

### 原则五：只保留有证据价值的示例

真人学习块应继续保留，因为它们提供了项目真实想要的口语证据。但每次只注入本次相关的少量
块，并明确其用途：

- `source_fill`：它是必须保持原句结构的模板；
- `human_rewrite`：它是语感参考，不是逐句复刻；
- `natural_generate`：不附加不相关学习块，给模型完整创作空间。

不建议在一个 Prompt 中同时提供全部模式的大段说明。应按本条实际模式动态加入一小段合同。

### 原则六：用评测决定是否保留规则

官方建议以现有可用 Prompt 为基线，每次移除一组指令后重跑同一批代表性任务。每条规则都应
回答：它修复了哪个已观察到的问题？如果没有对应失败样本或指标，就不应长期占据 Prompt。

## 推荐的新配置职责

### 项目配置只表达项目差异

建议未来将 `language_style` 简化为一个短 creative brief。示例仅用于说明目标结构，不表示
本轮直接修改 Schema：

```json
{
  "project_id": "taobao-12-no-threshold-redpacket",
  "category": "西瓜",
  "platform": "淘宝闪购",
  "benefit_points": [
    {
      "id": "primary-benefit",
      "text": "最高12元无门槛红包",
      "required": true,
      "exact_match": true
    }
  ],
  "creative_brief": {
    "audience": "日常即时零售用户",
    "communication_goal": "让用户先认同一个真实购买需求，再自然理解本次权益",
    "voice": "像朋友随口分享，具体、自然、有一点情绪，但不喊麦",
    "preferences": [
      "从最贴合商品的生活切口进入",
      "利益点只是促成购买的补充理由",
      "批量内容在人设、切口和节奏上拉开差异"
    ]
  },
  "validation_config_path": "../validation/strict-default.json"
}
```

这份配置不再规定固定六段式流程，也不枚举大量商品动作、开头句式、结尾句式和套话黑名单。

### ValidationConfig 只保留机器可判定项

适合继续放在验证配置中的字段：

- 字符范围；
- 明确禁用表达；
- 明确禁止或要求的行动引导；
- 格式前缀；
- 数字红包金额禁用；
- 必须逐字保留的活动字段。

不适合放进确定性校验：

- “听起来够不够自然”；
- “像不像朋友”；
- “开头是否足够抓人”；
- “情绪是否到位”；
- “生活场景是否有感染力”。

这些是语义质量，应由 Codex 自检、人工抽检和评测集评分，而不是关键词硬拦截。

## 推荐的精简文案 Prompt

以下是建议的目标形态，不是本轮直接替换生产模板：

```text
<task>
根据商品资料和活动资料，写一条可直接口播的中文短视频文案。
</task>

<context>
商品：{商品事实}
活动：{活动事实与必须逐字保留的利益点}
受众与传播目标：{项目 creative brief}
当前日期与季节：{时间上下文}
</context>

<success_criteria>
- 像真实用户分享一次购买或使用体验，不像详情页或活动播报。
- 选择一个与商品匹配的具体动机，自行组织最自然的表达顺序。
- 商品与利益点都清楚可听；利益点自然进入人物决定，不抢走全部注意力。
- 每句话提供新信息，不为凑字数重复或补空泛评价。
- 只使用已确认事实。
</success_criteria>

<hard_constraints>
- 必须保留：{required / exact-match / no-split 内容}
- 不得使用：{当前项目真正的合规禁用项}
- 目标 80–100 个中文字符，最终只输出一段正文。
</hard_constraints>

<source_mode>
本条模式：{source_fill | human_rewrite | natural_generate}
{仅插入该模式需要的简短规则和本次候选块}
</source_mode>
```

这个版本仍然保留事实和业务安全，但不再规定 20/50/30 比例、固定信息流顺序、固定钩子、固定
结尾、几十个反向示例，以及与本条模式无关的审计说明。

## 三种模式分别怎样减负

### `natural_generate`

只提供商品、活动、creative brief、硬约束和成功标准。不要附加真人块，也不要解释
`source_block_id` 等审计字段，让 GPT-5.6 充分发挥自然生成能力。

### `human_rewrite`

提供 1 个最终选定的真人块，而不是一组候选；只要求：

- 借用它的口语节奏或至少两个自然字眼；
- 重写为当前商品、需求和季节；
- 不恢复样本中的活动事实。

“至少两个锚点”如果只是为了审计可以保留，但应评估它是否迫使模型生硬塞词。可对比两个版本：

- 版本 A：继续硬要求两个逐字锚点；
- 版本 B：允许一个逐字锚点加一个结构/节奏说明，由 Codex 语义复核。

只有评测证明 A 的自然度没有明显下降时，才继续保留硬规则。

### `source_fill`

这是唯一适合保持低自由度的模式，因为目标就是保留原句。Prompt 只需要当前一个兼容块、当前
商品事实和“只填方括号”的合同，不需要同时携带自然生成和改写模式的全部说明。

## 建议保留、降级和删除的现有约束

| 当前要求 | 建议 | 原因 |
| --- | --- | --- |
| 不虚构事实 | 保留为硬约束 | 业务安全底线 |
| 必填、逐字利益点 | 保留为硬约束 | 活动合同 |
| NO_SPLIT | 保留为硬约束 | 下游字幕合同 |
| 禁止错误金额和活动口径 | 保留为硬约束 | 合规与项目隔离 |
| 当前季节冲突 | 保留为硬约束 | 可确定判断 |
| 80–100 字 | 先确认是否真是硬合同 | 可能导致凑字；若为配音刚需则保留 |
| 20/50/30 比例 | 删除 | 模型会把比例写成统一结构 |
| 固定六段信息流 | 降级为可选创意路径 | 不应每条强制 |
| 前三秒必须生活矛盾 | 降级为偏好 | 商品和人群不同，最佳开头不同 |
| 平台必须后置 | 仅对应项目保留为偏好 | 不是通用合规规则 |
| 结尾必须是习惯/状态 | 删除或降级 | 容易产生同质收尾 |
| 大量 `avoid_phrases` | 缩减为有回归证据的 3–5 项 | 减少反向注意力和误杀 |
| 动作示例长列表 | 删除，交给模型按品类判断 | GPT-5.6 可从上下文推断 |
| 每条都解释三种模式 | 改为只注入当前模式 | 降低无关上下文 |
| 50% `human_rewrite` | 作为批次实验变量 | 它是内容策略，不应永久写死而不评测 |

## 评测设计

不能仅凭主观感受直接替换现有 Prompt。建议建立一个小而真实的中文口播评测集，并保留当前
版本作为 baseline。

### 样本组成

至少包含 30 个任务：

- 10 个美食/饮品；
- 10 个日用品/家清个护；
- 10 个服饰、季节性或其他零售商品；
- 每组覆盖有具体卖点、只有品类、有利益点和无利益点；
- 至少两组 10 条批量任务，用于观察同质化。

### 对照版本

1. A：当前生产 Prompt；
2. B：只删除重复规则；
3. C：再删除固定 20/50/30 和固定信息流；
4. D：按模式动态 Prompt；
5. E：D 加精简 creative brief。

每次只改变一组因素，保证能判断是哪项调整产生效果。

### 硬指标

- 事实错误数量；
- 必填利益点通过率；
- 禁用表达通过率；
- 字数通过率；
- 批次重复和高相似率；
- 人工修改后才能使用的比例；
- 输入字符/token、生成耗时和失败重试次数。

### 人工质量评分

建议每项 1–5 分，并隐藏版本来源：

- 真人口语感；
- 商品与需求匹配度；
- 利益点融入自然度；
- 信息密度；
- 开头吸引力；
- 结尾自然度；
- 同批差异度；
- “是否愿意直接拿去配音”。

主要成功指标应是“可直接使用率”和“平均人工修改量”，而不是 Prompt 是否逐条体现了所有风格
指令。

## 分阶段实施建议

### 阶段一：只做去重

- 建立规则归属表；
- 删除基础模板与项目配置中的重复描述；
- 不改变事实、合规、利益点、字数和输出合同；
- 用现有任务做 A/B 回归。

风险最低，也最符合官方“每次移除一组指令后重跑评测”的建议。

### 阶段二：配置瘦身

- 把 `language_style` 的多层长字段改为精简 creative brief；
- 每个项目最多保留一个传播目标、一句 voice 和三条偏好；
- 将动作清单、固定开头和固定结尾从项目 JSON 移除；
- `avoid_phrases` 只保留有失败样本支持的少量项目特有项。

### 阶段三：按模式动态组装 Prompt

- `natural_generate` 不加载学习块规则；
- `human_rewrite` 只加载一个最终采用块及其短合同；
- `source_fill` 只加载一个块和填槽合同；
- 审计字段说明留在 Schema，不进入创作正文。

### 阶段四：验证器分级

- error：事实、活动、合规、格式等不能放行的问题；
- warning：套话、相似度、风格集中等可人工判断的问题；
- metric：自然度、修改量、可直接使用率等评测指标。

避免为了通过所有规则，把模型逼向同一个安全模板。

### 阶段五：用数据决定剩余策略

- 对比 50% `human_rewrite` 与更低比例；
- 对比严格 80–100 与目标区间加复核区间；
- 对比两个逐字锚点与更柔性的语义参考；
- 只在评测证明质量提升时保留更严格版本。

## 验收标准

优化完成应同时满足：

1. 同一创作规则在最终 Prompt 中只出现一次；
2. 项目 JSON 不再包含固定六段式流程和大段商品动作教学；
3. 每个项目的 creative brief 控制在约 150–250 个中文字符内；
4. `natural_generate` 不读取真人学习块合同；
5. 单条创作 Prompt 的固定部分明显缩短，动态内容只包含当前任务需要的信息；
6. 事实、利益点和合规通过率不低于当前版本；
7. 盲评中的真人口语感、利益点自然度和可直接使用率高于当前版本；
8. 批次同质化不恶化；
9. 输入 token、重试次数和人工修改量均有记录，不能只凭“感觉更好”验收。

## 推荐优先级

最值得先做的不是更换模型参数，也不是继续添加“更自然”的形容词，而是：

1. 删除重复规则；
2. 移除 20/50/30 和固定六段式等微观编排；
3. 把项目配置压缩为事实、目标、voice 和最多三条偏好；
4. 按当前 copy mode 动态提供最小 Prompt；
5. 用真实文案盲评决定是否放宽字数、锚点和 50% 改写比例。

在没有完成基线评测前，不建议直接启用最高 reasoning effort 或 Pro mode。OpenAI 的 GPT-5.6
指南建议先使用当前推理设置作为基线，再比较同级和低一级配置；只有代表性任务证明质量收益
值得额外延迟和成本时，才提高推理强度。
